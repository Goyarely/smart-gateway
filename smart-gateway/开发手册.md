## 一、项目代码地图（先记住这张图）

```
                      ┌───────────────────────┐
                      │  main.c  (应用层入口)   │
                      │  "总经理"：启动各模块    │
                      └──────────┬────────────┘
                                 │ 调用
                                 ▼
┌─────────────────────────────────────────────────────────┐
│  net_server.c  (网络层)   epoll 服务器                    │
│  职责：监听/接受连接/收发字节/连接生命周期                  │
│  它不懂"协议"，只管"字节"                                  │
└──────────┬──────────────────────────────────┬──────────┘
           │ 收到字节 → 写入                    │ 拆出完整帧 → 交给业务
           ▼                                  ▼
┌──────────────────────┐        ┌──────────────────────────┐
│  ringbuf.c (缓冲层)   │  ←→   │  protocol.c (协议层)      │
│  "蓄水池"：攒字节      │        │  "翻译官"：组帧/拆帧/CRC   │
│  解决粘包/半包         │        │  不碰网络，纯逻辑          │
└──────────────────────┘        └──────────────────────────┘

test/client.c (测试/设备模拟)  ←→  用 protocol.c 组帧，与服务器闭环
```

**核心设计思想：分层解耦。** 网络层不知道"帧是什么"，协议层不知道"网络怎么收发"。改协议不影响网络，改网络不影响协议——这是面试能讲的架构点。

---

### 2.2 `src/net_server.c` —— 网络层（epoll 服务器）

| 项 | 内容 |
|----|------|
| 职责 | 监听端口、接受连接、收发字节、管理连接生命周期 |
| 依赖 | `net_server.h` / `protocol.h` / `ringbuf.h` |
| 谁调用 | `main.c` 调用 `net_server_start()` |
| 它调用谁 | `ringbuf_write()`（存字节）、`ringbuf_try_parse()`（拆帧）、`frame_encode()`（回 ACK） |

**核心函数链**：
```
net_server_start()          ← 入口：三件套 + epoll 三部曲 + 主循环
   └─ 监听fd有事件 → accept循环（ET一次接完）→ 分配 conn_t → 挂进epoll
   └─ 连接fd有事件 → on_readable(conn)
                       └─ recv循环（ET一次读完）→ ringbuf_write
                       └─ 循环 ringbuf_try_parse → 有帧 → handle_frame
```

**读代码时要想的**：
1. `conn_t` 结构体为什么要有自己的 `ringbuf_t`？（每个连接字节流独立，不能混）
2. `ev.data.ptr` 挂的是什么？为什么用指针而不是 fd？（因为每连接要带自己的缓冲）
3. 断开连接时为什么**先存 `int fd = conn->fd` 再 free(conn)**？（use-after-free！free 后就不能访问 conn）
4. `handle_frame` 现在只打印+回 ACK——**这就是将来挂业务逻辑的地方**（里程碑 3 从这里长出来）。

---

### 2.3 `src/protocol.c` —— 协议层（组帧/拆帧/CRC）

| 项 | 内容 |
|----|------|
| 职责 | 帧的序列化/反序列化 + CRC 校验 |
| 依赖 | `protocol.h` |
| 谁调用 | `net_server.c`（回 ACK）、`test/client.c`（组帧）|
| 它调用谁 | 无（纯逻辑模块）|

**wire 格式（帧在网上的样子）**——一共 14 字节头 + payload：
```
偏移  字段     大小   说明
0     magic    2B    0xAA55 固定魔数
2     ver      1B    版本 0x01
3     len      2B    payload 长度（大端）
5     type     1B    命令类型
6     dev_id   4B    设备 ID（大端）
10    seq      2B    序列号（大端）
12    crc      2B    CRC16（覆盖前12字节+payload）
14    payload  N     （len 指定长度）
```

**读代码时要想的**：
1. 为什么用 `put16/put32` 一个字节一个字节写，而不是直接 `memcpy` 结构体？——**结构体有内存对齐**（padding），跨平台/跨编译器不可靠。这是协议层最大的坑。
2. `frame_decode` 返回三种值：正数=完整帧长度，0=数据不足，-1=坏帧。为什么要区分"数据不足"和"坏帧"？（一个要等更多数据，一个要跳过重同步）
3. CRC 计算范围为什么是"前 12 字节 + payload"而不是全帧？（CRC 字段自己不能算进自己）

---

### 2.4 `src/ringbuf.c` —— 缓冲层（环形缓冲）

| 项 | 内容 |
|----|------|
| 职责 | 解决 TCP 粘包/半包：攒字节 → 拆完整帧 |
| 依赖 | `ringbuf.h`（内含 `protocol.h`）|
| 谁调用 | `net_server.c` |
| 它调用谁 | `frame_decode()` |

**环形缓冲两个指针**：
```
tail(读) →  →  →  →  →  →  →  →  →  →  →  →  head(写)
         [已读走][未读数据........................][空]
```
- `ringbuf_used()` = head 和 tail 之间有多少字节
- 写：往 head 处写，head 前进
- 读（peek 偷看）：不移动 tail；确认拆出帧后才 `consume()` 移动 tail

**读代码时要想的**：
1. 为什么 `ringbuf_try_parse` 要"偷看不消费"？（拆不出来时数据还在，等下次 recv 补全）
2. 留 1 字节判空：`space = SIZE - 1 - used` 为什么留 1？（否则"空"和"满"无法区分——head==tail 到底空还是满？）
3. 坏帧为什么只跳 1 字节？（保守地逐字节找下一个合法帧头；跳太多可能错过）

### 2.6 头文件们（`protocol.h` / `ringbuf.h` / `net_server.h`）

| 头文件 | 给谁 include | 放什么 |
|--------|-------------|--------|
| `net_server.h` | 只有 main.c | 服务器对外接口 |
| `protocol.h` | 服务器 + 客户端 **共用** | 帧结构、命令枚举、编解码接口 |
| `ringbuf.h` | 只有 net_server.c | 环形缓冲接口 |

> 关键：**`protocol.h` 是"客户端和服务器共用"的那一个**——因为双方都要知道帧长什么样。其他头文件是"接口声明"，只给自己人用。

## 五、常见坑清单（踩过/易踩，面试可提）

| 坑 | 症状 | 原因 | 解法 |
|----|------|------|------|
| 端口被占用 | bind 返回 -1 | 上一个进程没退 | `sudo ss -lntp \| grep 8888` 查，kill |
| use-after-free | 断开后崩溃/乱数据 | free 后还用 conn 的字段 | 先存 `int fd` 再 free |
| 结构体对齐 | 帧解析错乱 | 直接 memcpy 结构体 | 逐字节 put16/put32 序列化 |
| ET 丢数据 | 长消息收不全 | ET 没循环读完 | recv while 循环到 EAGAIN |
| 环形缓冲满了 | 数据被丢弃 | 写满 | 检查 `ringbuf_used`，必要时扩大或断连 |
| errno 被覆盖 | 查错查不对 | 多个系统调用共用 errno | 出错**立即**检查 errno |

## 六、面试问答卡片（每里程碑攒的，直接背）

**里程碑 1（网络层）**：
1. Q：为什么用 epoll 而不是 select / 多线程？
   A：epoll O(1) 获取就绪事件、单线程扛千连接、ET+非阻塞减少系统调用；select O(n) 且 fd 上限 1024；多线程每连接一栈 8KB 浪费内存。
2. Q：LT 和 ET 的区别？
   A：LT 有数据就提醒，读不完还会提醒；ET 只在"从无到有"变化时提醒一次，必须一次读完（读到 EAGAIN）。
3. Q：recv 返回 0 / 正数 / -1 各是什么？
   A：0=对端关闭；正数=收到字节数；-1=出错，其中 EAGAIN 表示非阻塞下暂时没数据。

**里程碑 2（协议层）**：
4. Q：TCP 粘包怎么解决？
   A：长度字段 + 环形缓冲拆帧。收到的字节先进缓冲，用"偷看不消费"试拆，拆出完整帧才消费。
5. Q：为什么不用裸 JSON？
   A：二进制帧定长字段、解析快、带宽小；JSON 文本解析慢、有分隔符歧义，不适合嵌入式。
6. Q：CRC 能发现什么错误？
   A：所有单比特错、双比特错、奇数位错；坏帧直接丢弃并计数。
7. Q：为什么每个连接一个环形缓冲？
   A：各连接的字节流独立，混在一起会把 A 的半包接到 B 的流里。
